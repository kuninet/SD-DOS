# 複数クラスタ読みの既存挙動の確認結果

## 目的

シーク機能の調査([ストリーム読み出しのシーク機能の要否](seek.md))で見つかった、`GET_FP_CLSTR`の前提(`FP_CLSTR`=先頭クラスタ#)と読み出し経路`NEXT_CLSTR`の動作(`FP_CLSTR`をカレントクラスタへ更新しつつ`FP_CLSTR_SN`も加算)の整合に関する疑義を、実際にアセンブルしたコードの実行で確認する。

## 検証方法

j80エミュレータはSDドライブのハードウェアをエミュレートしないため、次の方法で確認した。

* アセンブル済みのSD-DOS本体(`MAIN.asm`の`-raw`出力)をZ80インタプリタ(`scripts/z80mini.py`)で実行する
* SDからのセクタ読み込み(`READ_SCTR`)だけをフックし、ホスト側で用意したFAT16相当のセクタイメージから供給する
* FAT関連ワーク(`SCTRS_PER_CLSTR`、`FAT_SCTR`、`DATA_SCTR`、`TGT_CLSTR`など)をMOUNT相当の状態に設定する
* `PREP_READ`を呼んだ後、`FETCH_1BYTE`をファイルサイズ分繰り返し、取得バイト列と期待値を比較する
* クラスタ跨ぎを起こしやすくするため1クラスタ=2セクタとし、内容は周期251のパターンで配置ずれを検出できるようにする

検証ハーネスは`scripts/test_multicluster.py`にあり、再実行できる。

```sh
printf 'OK\n' | java -jar tools/tools80.jar -tgt=z80 -raw -debug -sym src/MAIN.asm
python3 scripts/test_multicluster.py src/MAIN.raw src/MAIN.sym
```

## 結果

| ケース | 内容 | 結果 |
|---|---|---|
| C: 1クラスタに収まるファイル | 1000バイト | 全バイト一致(対照ケース。ハーネス自体の妥当性も確認) |
| A: 3クラスタにまたがるファイル | 2660バイト | 2クラスタ目の先頭(1024バイト目)から不一致 |
| B: クラスタ境界ちょうどで終わるファイル | 2048バイト | 1024バイト目から不一致。最終バイトの取得で`ERR`に到達 |

ケースAのセクタ読み込みログでは、2クラスタ目(クラスタ#3)に入った時点で、クラスタ#3のセクタではなく**1つ先のクラスタ#4のセクタが読まれる**ことが確認できた。取得データも2048バイト目以降の内容と一致しており、クラスタ1つ分先のデータを読んでいる。

ケースBでは、2クラスタ目でFATの終端(0FFFFH)を越えた範囲のFATを読みに行き、データは不正になる。また最終バイトの取得時に`INC_FP`の先読みが`NEXT_CLSTR`で0FFFFHに到達し、`MSG_SCTR_OVERFLOW`の非復帰エラーへ進むことも実証された([ストリーム読み出しのEOF・エラー・長尺ファイルの扱い](eof-error.md)で整理した挙動のとおり)。

## 原因

`FP_CLSTR`と`FP_CLSTR_SN`の使い方が、経路によって異なることによる二重カウントである。

* `GET_FP_CLSTR`は「`FP_CLSTR`=ファイルの先頭クラスタ#」を前提に、FATを`FP_CLSTR_SN`+1回たどって目的クラスタを求める
* 一方、読み出し経路の`NEXT_CLSTR`は、クラスタ境界のたびに`FP_CLSTR`を次のクラスタ#へ更新し、同時に`FP_CLSTR_SN`も加算する
* このため2クラスタ目以降では、`GET_FP_CLSTR`が「カレントクラスタからさらに`FP_CLSTR_SN`回」FATをたどり、シリアル#の分だけ先のクラスタを読む

書き込み経路(`INC_FP_W`)は`FP_CLSTR`をカレントとして更新するが`FP_CLSTR_SN`を増やさないため、この問題は起きない。`SET_FP_END`は`FP_CLSTR`=先頭のまま使うため、これも問題は起きない。読み出し経路だけが両方を更新するため不整合になる。

## 既存機能への影響

* クラスタサイズを超えるファイルの`LOAD`、`RBYTE`は、2クラスタ目以降で正しくないデータを読む
* 2GBのSDメモリカード(FAT16、1クラスタ=32KB)では、32KBを超えるファイルで顕在化する。通常の用途(32KB以下のプログラム)では表面化しないため、潜在していたと考えられる
* この挙動はFork元のコードに由来するとみられる

## ストリーム読み出しへの方針

ストリーム読み出しは複数クラスタの長尺ファイルが主用途であり、この問題の影響を直接受ける。前提として次の方針を置く。

* この不整合は、ストリーム読み出しAPIの実装に先立ってバグ修正として対応する。最小修正は、(1)`FP2SCTR`が`GET_FP_CLSTR`を呼ばずに`FP_CLSTR`を直接使う、(2)`SET_FP_END`は`GET_FP_CLSTR`の結果を`FP_CLSTR`へ格納してカレント規約に揃える、の2点で、書き込み経路はそのまま成立する
* 修正により、ストリーム読み出しは既存の`READ_FP_SCTR`、`INC_FP`をそのまま再利用できる([ストリーム読み出しAPI仕様](api-spec.md))
* 既存動作の修正は「既存コマンドの挙動を変えない」方針の例外(バグ修正)として扱う
